# MPL 理论能力边界与阶段划分（V0.0.3）

本文只定义职责边界与接口方向，不表示 V0.0.3 已实现这些能力。

## 1. 三个阶段

```text
1. 音乐程序合成
   源码 / 自然语言 / DAW 操作 / 可视化前端
   → 定义、意图、参数、约束

2. 确定性编译
   Music IR / Temporal IR / Production IR
   → 诊断、增量重算、工程与事件导出

3. 音频运行
   Audio Graph / DSP / 实时调制 / 空间化 / 采样域求值
   → 音频信号
```

V0.0.3 完成第 2 阶段的基础：时间语义、实例、自动化、确定性导出。第 1 阶段的文本前端与第 3 阶段的音频运行时尚未实现。

## 2. AudioSignal 与 EventStream

- **EventStream**：稀疏、带时间戳的音乐事件（音符、CC、参数变化），由编译期/工程层产生，适合 MIDI、DAW 工程和离线分析。
- **AudioSignal**：连续采样信号，由音频运行时产生，携带采样率、通道布局与块处理语义。

边界规则：

- Music/Temporal/Production IR 只描述 EventStream 与参数，不直接持有 AudioSignal。
- SoundBoxer 后端负责把 Production IR 映射为 Audio Graph，并产生 AudioSignal。
- 音频分析结果回流到编译期时，必须作为显式的分析数据/约束，而不是隐式的运行时副作用。

## 3. Stateful Processor

有状态处理器（滤波器、压缩器、混响、侧链）属于音频运行阶段：

- 编译期只描述处理器图、参数目标与自动化曲线。
- 运行期负责状态、块边界、延迟补偿与实时安全。
- 状态初始化/重置规则必须由处理器类型声明，不能由 Core 猜测。

## 4. 空间音频语义

保留方向：

- 声源/听者位置、距离模型、声道布局、空间化算法属于运行时或后端能力。
- Core 可以表达“空间参数目标”（如 azimuth、distance）及自动化，但不定义具体 HRTF/Ambisonics 实现。
- 参数单位与范围由目标声明，后端负责映射。

## 5. 稳定随机流

生成性算子必须显式携带：

- seed；
- 流标识（同一 seed 下的子流划分）；
- 算法/模型版本；
- 输入上下文摘要。

要求：相同 seed、版本与输入产生相同输出；不同版本不得静默复用旧随机序列。V0.0.3 没有生成性算子。

## 6. 生成式自动化

生成式自动化（例如“让滤波器随张力变化”）属于可选扩展：

- 输出仍是 Temporal IR 曲线或参数事件，不直接产生音频；
- 必须记录生成模型版本、seed、输入特征与预算；
- 失败时保留确定性回退曲线，而不是让编译结果不可复现。

## 7. 感知意图与情绪轨迹

“更明亮”“更紧张”“更有空间感”属于感知意图层：

- 可以表示为高层目标/轨迹（时间 → 目标特征）；
- 需要由可替换的感知策略后端映射为具体参数曲线；
- Core 不硬编码情绪词汇、审美偏好或风格规则。

## 8. Taste Profile

Taste Profile 是用户/项目级偏好数据（风格、响度、音色倾向、禁忌）：

- 不属于 Music IR 语义；
- 以独立数据输入编译流程；
- 必须可审计、可关闭、可替换；
- 不得成为隐式全局状态。

## 9. 可替换 Perceptual Strategy Backend

接口方向：

```text
Intent / Trajectory / TasteProfile / Analysis
        ↓
PerceptualStrategyBackend
        ↓
Temporal IR curves / parameter targets / constraints
```

约束：

- 策略后端可以是规则、优化器、模型或人工决策；
- 输出必须落到可序列化的曲线/参数/约束；
- Core 只定义接口与验证，不定义“好听”的标准；
- 失败必须产生诊断与确定性回退。

## 10. 明确不进入 Core 的内容

- 情绪识别与音频审美评分；
- 具体生成模型权重与推理运行时；
- 实时 DSP 调度器；
- 具体空间音频算法；
- 用户偏好学习算法。

这些能力应通过标准库、扩展接口、后端插件或真实音乐案例驱动，而不是继续扩大 Core 前置范围。
